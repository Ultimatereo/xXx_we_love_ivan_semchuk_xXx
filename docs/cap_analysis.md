# CAP Analysis for HealthTech EHR

## Why Medical Records Are CP
Для диагнозов, аллергий и критичных назначений система должна предпочитать `Consistency + Partition tolerance`.

Причина: конфликт версий в медкарте может привести к прямому медицинскому риску.
Примеры риска:
- в одной партиции добавлена аллергия на препарат, в другой партиции запись отсутствует;
- при merge версий врач может получить устаревшую карту и назначить противопоказанное лечение.

Поэтому при сетевом разделении (split-brain) запись таких данных должна отклоняться.

## Split-Brain Behavior
При partition между кворумами:
1. Узел/группа без кворума не принимает write в CP-зону.
2. API возвращает ошибку доступности (`503 Service Unavailable` или доменный аналог).
3. Система избегает double-write и divergence версий.

Это сознательный компромисс: временно ниже availability, но безопасная консистентность.

## What Can Be AP-like
Телеметрия из реанимации может работать в более мягкой модели:
- данные пишутся в append-only WAL локально;
- допускается буферизация и поздняя доставка;
- eventual consistency приемлема для агрегатов и трендов, если критичные алерты имеют локальные fail-safe правила.

Потеря части свежей телеметрии неприятна, но обычно менее критична, чем конфликт диагноза/аллергии.

## Recommended Replication Strategy
Для CP-зоны медкарт:
- leader-based replication;
- quorum write/read (например, `W=2, R=2, N=3`);
- fencing tokens или term-based leadership для защиты от stale leader.

Для аналитики и поисковых read-путей:
- read replicas;
- асинхронная репликация;
- eventual consistency допустима для вторичных витрин и отчетов.

## Degradation Policy
Можно деградировать по доступности:
- запись диагноза,
- запись аллергии,
- изменение критичных назначений.

Можно деградировать по консистентности (в разумных пределах):
- поисковые индексы,
- аналитические отчеты,
- неоперационные дашборды.

## Final Principle
В медицинских системах конфликт версий часто опаснее, чем временный отказ в записи.
Поэтому для критичных данных оправдано правило: лучше вернуть отказ по availability, чем принять противоречивую запись.
